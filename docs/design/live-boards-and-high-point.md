# Live Boards And High-Point Standings

Read before changing the Results Board, the Results & High Point board, the Gate Board, the marquee, points systems, a show's own chart, circuits, or the leaderboards. Posting results, which both results boards read, is in [results-and-scoring.md](results-and-scoring.md); the gate the Gate Board reads is in [gate.md](gate.md).

These are the rules this part of the app keeps and the reasons behind them, moved here from `Claude.md` so they load when the work needs them rather than on every request. One claim per bullet, the claim first. Add new ones under the heading they belong to.

## The live boards and the marquee

- `show_marquees`: **what the marquee along the bottom of the live screens carries** (migration 139) — `results` (the default, and what no row means), `message`, `both`, or since migration 158 `high_point` — the high point standings, a line per division, the same top five as the split board (`highPointLines`), offered on both boards' pages because the marquee is one setting for the show; refused at a show with no points chart, the page greying it out with a `title` from `high_point_available` on the marquee payload, and the Results Board's page fetches the leaderboard only while it is chosen — plus one line of text. Set on the Results Board page (`/admin/shows/[id]/board/results`, opened bare — reached from the Live Screens page at `/board`) by the show office through `PUT /shows/{id}/marquee`, and **stored on the show rather than in the browser**, so a running board picks a change up on its ordinary 12-second poll wherever it is. The message survives a switch back to `results`; a message mode with nothing typed is refused, and `effective_mode` on the public `GET` falls back to `results` regardless, because a marquee must never scroll a blank band. Its own table rather than columns on `shows`, since `_serialize` builds the show payload by hand and this is not show configuration. **The board's header also carries a QR code** (top right, `components/QrCode.tsx`) to the show's public **Results** page, `/shows/[id]/results` — the at-the-rail screen that stays public precisely so a phone can open it with no account. The URL is built from the address the board itself is on, so it is right in every environment. **The board can run on a monitor plugged into the laptop or tablet, extended or duplicated.** *Extend screen* on the Results Board page opens it in a window of its own (`openOnSecondScreen`) — opened first, while the press still counts as a gesture, then moved and sized onto the other monitor through the Window Management API (Chrome and Edge; elsewhere, or with the permission refused, it stays a window to drag across). The board in that window (`?popout=1`) asks for one press on **Fill this screen**, since a browser goes full screen only on a press in that window. The device it came from stays usable. *Duplicate screen* is for a monitor mirroring the device — a tablet mounted on the back of a TV, which cannot extend: the board starts in this tab and asks for full screen on the same press, so the monitor shows the board and not the browser's bars; `?duplicate=1` makes it ask again whenever it is not full screen, and it holds a screen wake lock (`useWakeLock`), because a tablet that auto-locks takes the mirrored monitor dark with it. **A second board, *Results & High Point*** (`/board/results-high-point`), is the same `LiveBoard` with `layout="split"`: the class on the left two judges' cards at a time, **its division's** high point standings on the right — **one division at a time** (`buildSplitTurns`): the table holds while each of that division's classes posted today takes its turn beside it, then both halves move to the next division together, in the show's division order; a division with standings but no class today still gets a turn, its table beside a notice, and classes in no division come last, beside "earns no high point" — then, last of all, the classes the office left out of high point (migration 167), beside a notice that they do not count, because set beside their division's table a room would read their winners as having earned its points. The halves used to turn independently, two tables at a time, and a room reading an Amateur class beside the Open and Youth tables had to work out which one its horse was in. Divisions match by name the way `high_point._division_key` does (`divisionKey`). **Both halves are headed alike** (`SplitHeader`, one component): *Class Results* with the Top 5 badge and the class named beneath it in the accent colour, across from *High Point* with the badge and the division named beneath it. The left half was headed by the class name itself while the right said *High Point* with its division inside the box, so the two halves read as two different kinds of screen; the division's name moved up out of the box so both read the same two lines and their boxes start level. The two-line header is pinned taller (`SPLIT_HEAD_UC`, which `scaleFor` counts). The rows are laid out like placings with the rosette and the back number (`topStandings` in `lib/high-point.ts`), both halves on one scale and one clock — so everything above applies to it unchanged. The QR code is drawn from the symbol's module matrix in the board's own colour tokens rather than taken as the library's SVG string, which carries literal colours.

## Every board is one kind of screen

- **The screen half of a board is shared** (`board/_components/`): the three sizes and the two units they set (`units.ts`), full screen, *Duplicate* / *Extend screen* (`second-screen.ts`), the wake lock, the fade-in controls, the header with its clock, and the page in front of the board with its *Where is this screen?* question (`BoardSetup.tsx`), all driven by `useBoardScreen`. A TV set up for one board is set up for all of them, and F, 1, 2 and 3 do the same thing on each. `LiveBoard.tsx` kept only the results; it had held all of this inline, and the gate board would have been a second copy of it.
- **Each board opens its own named window** when extended (`openOnSecondScreen`'s `windowName`): the two results boards share `gaitdesk-results-board`, as they always did, and the gate board has `gaitdesk-gate-board`, so a results board and a gate board can each have a monitor of their own from one laptop.

## The Gate Board

- **For the riders who are not in the ring yet** (`/admin/shows/[id]/board/gate`): *In the ring* is one line naming the class, or the classes run together, and **lists nobody** — the riders in the ring are not the ones reading it. *On deck* and *In the hole* sit side by side, each class's riders in the gate's order of go with a **✓ once checked in**; *Coming up* names the classes after them. Its order of go is left off on purpose: the board is there to show who is not in yet.
- **The blank beside a rider is the message.** A checked-in rider has a ✓, a no-show is struck through and says so, and a rider the gate is still waiting on has nothing — a rider who finds their number with no ✓ beside it knows to report to the gate. The count over each class ("4 of 6 checked in") is out of the riders still expected, since a no-show is not coming.
- **One ring to a board.** A gate TV sits at one ring's gate, so a show running two rings puts up two boards. The board's page asks which ring (`?ring=`) only when the show has more than one, and the sizes stay greyed out with a `title` until it is answered. A ring no longer on the show is no answer, and the page asks again.
- **The board follows the gate steward and nothing else.** *In the ring* is what the gate has started; a class is over once the gate finishes, skips or closes it; *On deck* is the first class the gate has not started — `gate_rules.on_deck`, the steward's own rule (`gateLane`). **Posted results do not move it.** It first read the public schedule's live badge (`classProgress`), which also counts a posted class as over and every class above it with it; one class posted further down the day — class 7 at a show with riders still waiting in 2 to 4 and nothing started — closed them all, and the board read *That's the day*. The board is the gate's, so it calls riders by what the steward has done at the gate. The schedule keeps its rule, so the two can disagree where posting runs ahead of the gate; a show that never works the gate has a board stuck on its first class, and there is no check-in for it to show either.
- **A class nobody is entered in is passed over**, not called — the gate skips it, and the riders of the class after it are the ones who need to be getting ready. Draft classes are not on the board, as they are not on the schedule.
- **The day is the reader's**: today when the ring runs classes today, before the show the next day it does, after it the last. Never the first day with something unfinished — a class nobody marked done on Saturday would hold the board on Saturday all through Sunday (`boardDay`).
- **It polls the gate from the browser, every 10 seconds**, rather than re-rendering on the server like the results boards: which classes are called depends on the day, and a server renders in UTC, hours out by evening. It reads the steward's own endpoints, `GET /shows/{id}/gate/classes` and `.../classes/{cid}/entries` for the two classes called, which the show office may read — so the board exposes nothing new and needed no backend change. The riders of the classes already on screen are asked for alongside the class list, so a board just put up waits one round trip and not two; a class the fresh list calls instead is a second request in the same poll.
- **Riders are numbered only where the order is kept**: a class worked one at a time (scored, equitation, timed) or one whose order the steward set by hand or by draw. A rail class rides in together, and numbering its back numbers 1 to 12 would read as a running order nobody is keeping (`numbersOrderOfGo`).
- **A long class shrinks before it pages.** Its riders are drawn down to three-quarters size, in two columns wherever each column can stay wide enough for a rider's name beside the back number (`MIN_COL_U`), and only then paged on the board's clock, with dots beside the label (`fitRiders`). **Riders run down the pane to the bottom before a second column starts**, and a class that fits one column gets one at the pane's full width; the rows were first split evenly between two columns (ten riders as five and five), which the office did not want, and a half-empty second column only took width from the names. The page range was printed as "5–8 of 8" at first, and at the lobby size it pushed the check-in count off the pane.
- **A failed poll keeps the last picture and says so**: the header reads *NOT UPDATING* in place of *LIVE*. A board read from across a room cannot be refreshed by the people reading it.
- **No marquee yet.** The marquee is one setting for the show, and its results mode scrolls placings a gate has no use for; whether the gate board carries the office's message is still to decide.

## High-point standings

- `point_systems` / `point_system_awards` / `show_point_systems` / `circuits` / `circuit_shows`: **high-point standings** (migration 147). The public Leaderboard was a "coming soon" card that computed nothing. **A points system is data, never code, and **the associations' own charts are entered from their published rules and nothing else** (migration 151, GaitDesk standard systems): APHA SC-060.A.1, ApHC rule 701.A, FQHR's F.Q.H.R. Points, NSBA's traditional and year-end charts, and WSCA's color points and Championship Show points, each citing its rule and edition in `notes`. **AQHA is deliberately absent** — its rulebook could not be read from an American source, and a chart copied from elsewhere would be read at the rail as AQHA's; MNSPHC publishes no chart. Do not add a chart the association has not published** — every association scores its own way, most of them scaled by class size, and a chart typed from memory under APHA's name would be read at the rail as APHA's. **It belongs to a show company** (`point_systems.company_id`, migration 148): the company's managers and secretaries enter the charts their shows score by at `/admin/point-systems`, and **only the company's own people see it or can choose it** for a show or a circuit (`high_point.may_use_point_system`; another company's system is a 404, not a 403, since its name is that company's business). A GaitDesk admin sees and manages every company's. **A system under no company is a GaitDesk standard one**: every company sees it and may choose it for a show or circuit (`high_point.may_use_point_system`), but only an admin may change or delete it (`may_edit_point_system`; a company gets a 403 telling it to use the chart as a template instead, and the screen offers *Use this template*). Names are unique within their owner, so two clubs may each keep an "APHA Open Show Points". What is scoped is who may *pick* a chart, never who may read one: the public leaderboards print whatever chart a show scores by. A show already on another company's system keeps it — the picker shows it by name as *another company's* — until somebody chooses again. **Deleting a company deletes its systems, and is refused while one still scores a show or circuit** (`routers/show_companies.delete_company`): left behind with no company, a club's private chart would read as a GaitDesk standard one and appear in every other company's list. `ON DELETE SET NULL` stays as the backstop, not the path. `point_system_awards` is the chart as bands: from a class of `min_entries` horses up, `place` earns `points` (NUMERIC, because charts award half points); **the largest band at or below the class size applies** and a class smaller than the first band earns nothing, which is how a printed chart's "11 or more horses" row reads. **A row is a range of class sizes, and pays as many places as the largest class in it** (migration 152): rows are stored by their first size only, so a row runs to one below the next row's start — rows at 3, 5 and 10 are 3–4, 5–9 and 10 or more — and a 5–9 row may pay down to 9th. The last row is open-ended and pays at most its first size. `high_point.place_limits` is the rule, enforced by the router's 422 and the editor's greyed-out cells; it cannot be a CHECK because the top of a range is another row, so 152 dropped the stricter `place <= min_entries` CHECK migration 150 had added. A flat 6-5-4-3-2-1 scale is two rows, 1–6 and 7 & over. In the editor, typing where a row ends starts the next row one higher, and a cell past a row's range keeps what was typed but is greyed out and not saved — narrowing a range never wipes a row, since typing "14" passes through "1". A row with no points is refused, because saving without it would stretch the row above over its range. The show's office picks its system (`show_point_systems`, a table rather than a `shows` column for migration 146's reason; no row, no standings — the page says so rather than guessing a chart). **Since migration 153 a show keeps a chart of its own**, set in **setup Step 8, Scoring**, beside the judge cards, and on the High Point page the dashboard tile opens — the same `ShowPointChart` behind both doors. Either offers every template the caller may use plus **Custom** (an empty chart), shows the matrix before anything is chosen, and *Use this template* opens it in the same grid editor the library uses (`components/PointChart.tsx`); saving writes a `point_systems` row with `show_id` set — no company (a CHECK), one per show (a partial unique index), deleted with the show — and scores the show by it through `PUT /shows/{id}/high-point/chart`. **The template is untouched**, so a later correction to it does not move this show's standings. **A show's chart is never in the library**: `may_use_point_system` / `may_edit_point_system` refuse it for everybody, an admin included, so it is not listed, not offered to another show or a circuit, and not editable at `/point-systems/{id}` — without that it would read as a GaitDesk standard one, having no company. Moving the show off it deletes it, since nothing else can reach it. In the wizard, leaving the step with the editor open saves it like every step (`useRegisterStepAutosave`), but only when there is something to save — a template just opened, or a chart that differs from the saved one. `GET /shows/{id}/high-point` reads the chart without the standings, for the wizard; the public leaderboard computes every posted class to answer the same question. A show still on a library system as it stands keeps it, with *Customize for this show* to take a copy. `show_point_systems.point_system_id` is NO ACTION rather than RESTRICT, so deleting a show can remove the choice and the chart in one statement. A **circuit** is a season: several shows added up under the circuit's own system, managed by whoever created it (or an ADMIN), a show added only by somebody who works it, and removable by the show's own office. **The standings are derived on every read, never stored** (`backend/high_point.py`), so posting a class moves the leaderboard and changing the chart rescores everything. The rules, pinned by `tests/test_high_point.py`: only **posted** classes count, and only those the office has not left out (`classes.high_point_eligible`, below); **each judge's card earns its own points** (how breed points are earned — not a combined result); class size is the horses shown — the class's entries less scratches and **no-shows at the gate** (`entries.gate_no_show`, migration 162), since a horse that never entered the ring was not shown; only a placed card earns (`placings.is_placed`); a tie earns both horses that place's points; standings are **per division, per horse and rider, added up across every discipline** — Amateur Halter and Amateur Western Pleasure both count toward one Amateur table — matched by name across a circuit's shows, and the show's leaderboard carries each exhibitor's back number there (a circuit's does not: one exhibitor has a number per show), ranked 1, 2, 2, 4. Admin screens: `/admin/point-systems` and `/admin/circuits` (ADMIN, managers, secretaries), and a **High Point** tile on the show dashboard. Public: `/shows/[id]/leaderboard` (refreshes itself while ACTIVE) and `/circuits/[id]`.
- `classes.high_point_eligible`: **a class the office leaves out of high point** (migration 167). Every posted class used to add to the standings, and shows run classes that are not part of their high point — a leadline, an open jackpot, a fun class — so a placing in one was added in with the classes that count. TRUE by default, so no standing moved. `high_point.load_cards` skips a class left out, which is what the show's leaderboard, both results boards, the marquee and every circuit add up, so they agree; the class is still judged, posted and on every results page, and `posted_class_count` still counts it. Set a tick per class, or a division at a time, on the High Point page and folded under the chart in setup Step 8 (`HighPointClasses` — one implementation, two doors, like `ShowPointChart`) through `PUT /shows/{id}/high-point/classes`, **one request at a time**: every answer is the whole class list, so two in flight could land out of order.
- **What each class put up for grabs is printed beside the standings, from the standings' own arithmetic** (`high_point.class_points`, `summarize_class`, `load_class_summaries`). Per class: the entries (the horses shown — the class size the chart reads, scratches and gate no-shows left out), what first place earns on one judge's card, and the points up for grabs — every place the class can pay, on every card, the cards being the judges on the panel (or the cards filed, where there are more). A class is worth no deeper than its size: a 5–9 row may pay down to 9th, but a class of six has no 7th place. On the public leaderboard (`classes` on `GET /shows/{id}/leaderboard`, posted classes only — the ones the standings are added up from) and on the High Point page (`GET /shows/{id}/high-point/classes`, every class, so the office reads a class's worth as the entries come in). **A class left out is listed and marked, not dropped**, so a placing in it is not read as points gone missing. `components/HighPointClassPoints.tsx` draws both and computes nothing: a second copy of the arithmetic is how a table comes to disagree with the totals beside it.
