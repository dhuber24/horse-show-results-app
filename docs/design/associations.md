# Associations, Their Rules, Memberships And Class Codes

Read before changing association validation (`backend/rules/`), membership or competition-card handling, show categories and APHA readiness, or the class-code catalog. The rule-by-rule narrative is in [apha.md](../apha.md) and [aqha.md](../aqha.md).

These are the rules this part of the app keeps and the reasons behind them, moved here from `Claude.md` so they load when the work needs them rather than on every request. One claim per bullet, the claim first. Add new ones under the heading they belong to.

## Associations and show types

- `associations`: **the registry of bodies a horse or person is affiliated with**, typed `breed` (AQHA, APHA, ApHC, FQHR) or `club` (NSBA, WSCA, MNSPHC) — migration 080, MNSPHC added in 105. Everything that stores a registration or membership number points here: `horse_registrations`, `exhibitor_registrations`, `trainer_registrations`, `exhibitor_documents`, `show_secretary_certifications`. This is **not** the same concept as `show_types`: a show type is show configuration ("what kind of show is this?"), while an association is a property of the horse or person ("this horse is registered with AQHA"). The same code appears in both lists on purpose. There is no `associations` row for OPEN — Open means *no* breed association.
- `OPEN` is an unaffiliated **show type** only. Since migration 080 it has no `associations` row at all, so it can no longer leak into certification or registration-number pickers — the old `UNCERTIFIED_CODES = ['OPEN']` guards were removed as dead code. Do not re-add OPEN to `associations`.
- Do not reach for `show_types` when you mean an affiliation. Registration/membership numbers belong to `associations` (breed or club); `show_types` is show configuration. Clubs (NSBA, WSCA) are deliberately **not** show types — an NSBA-approved show is an OPEN or breed show carrying NSBA sanctioning via `show_sanctioning`.
- `class_associations`: association-specific codes for a class, useful for dual-sanctioned shows.
- `backend/rules`: association-specific validation hooks; AQHA currently enforces the first practical validation slice.
- `users.aqha_management_workshop_completed_at`: AQHA show-management workshop date used to validate assigned managers/secretaries.

## Memberships and competition cards

- `exhibitor_registrations`: exhibitor membership numbers per association, plus `expires_at` — **required on a breed association since migration 134**, still optional on a club. **The expiry is reported beside the verification status, never folded into it** — `status` answers "has anybody at this desk inspected the card?" and `lapsed` answers "is the card good?", the same split health paperwork already makes. Judged against `shows.end_date`, never today: a membership that lapses on the Saturday of a three-day show is exactly what the office needs to chase. NULL means *unknown*, not current, and the desk says so rather than showing green. The pre-080 `exhibitors.apha_member_number` / `apha_member_expiry` columns are backfilled here by 117 and deliberately left in place — some records carry a number only there, and dropping the sole home of somebody's membership number is data loss, not a migration.
- **A breed membership needs an expiry date and a club membership does not.** NULL has meant *unknown* rather than current since migration 117, and a breed body's good standing is a condition of showing (APHA RG-030) — so `POST`/`PATCH /exhibitors/{id}/registrations` refuse a breed row without one. A club is the softer case and stays optional: several clubs sell a membership at the gate, plenty run to no fixed date, and refusing the number over the missing date would lose the number too. Enforced in `routers/people.py` rather than by a CHECK, which cannot see `associations.association_type`. `PATCH` exists **because** of this rule — rows filed before it carry no expiry, and without an edit path the only way to satisfy it would be to delete the membership and retype the number.
- `exhibitor_competition_cards`: **the card that lets somebody enter a division, and the one date every one of them expires** (migration 134). APHA gates Amateur, Novice Amateur, Amateur Walk-Trot, Novice Youth and Youth Walk-Trot 11-18 on a card rather than on age or membership alone, and each runs 1 January to 31 December and is renewed annually — apha.com/competition/amateurs ("Amateur cards run January 1–December 31 and must be renewed annually") and APHA's own entry form ("ALL APHA AMATEUR, NOVICE AMATEUR, AMATEUR WALK TROT, NOVICE YOUTH AND YOUTH WALK TROT 11-18 CARDS EXPIRE DECEMBER 31ST"). **So there is no expiry column**: the row holds `valid_year` and `competition_cards.card_expiry()` derives 31 December of it, exactly as a horse's age is derived from its foaling date. A date box would take 2026-06-30 — not a card APHA issues — and the desk would read it back as authoritative. **Renewing is raising the year**, which is what an annual renewal is. One row per `(exhibitor_id, association_id, division)`, because somebody legitimately holds an Amateur card and a Novice Amateur card in the same year; `division` reuses `entries.apha_division`'s vocabulary (migration 115) since a card is what entitles an entry to name that division. The legacy `exhibitors.amateur_card_number` / `_expiry` / `amateur_novice_codes` columns (migration 010) are backfilled here and left in place, the same call migration 117 made. Recorded on the profile's Memberships tab, below the memberships; nothing refuses an entry over one.
- **A competition card stores a year, and the expiry is the rule rather than a fact about the card.** Every APHA card the app models expires 31 December, so `competition_cards.card_expiry()` is the single place that is written down and `exhibitor_competition_cards` has no date column at all. Do not add one "so a card with an unusual expiry can be recorded" — there is no such card, and the box would be typed wrong on the ordinary ones. **Two divisions are missing on purpose**: plain Youth and Youth Walk-Trot 5-10 are not on APHA's notice, youth eligibility being age and youth membership, and adding them for symmetry would have the app chasing paperwork nobody issues. `is_current(valid_year, as_of)` takes its date rather than defaulting to today, the same rule membership expiry and health paperwork follow: a show office asks whether the card covers *the show*.
- **`CARD_DIVISIONS_BY_ASSOCIATION` knows only APHA, and that is a statement about this app rather than about the associations.** AQHA's card rules have not been supplied, and a guessed year-end would be filed on a profile, read at a desk and found out at a gate — the same reasoning that keeps invented penalty labels out of the `judging_penalties` seed. Adding a body is one entry in that map once its rule is in hand; the CHECK constraint deliberately does not encode who issues what, so it takes no migration.

## Show approval and show category (APHA)

- `shows.apha_zone`: **APHA zone 1-14** (migration 119), NULL meaning *not stated*. Nothing derives it from the venue's state — a guessed zone is wrong at exactly the shows that sit near a border. Only one of its five uses is actionable today: in **Zones 12, 13 and 14** equitation and horsemanship are worked individually from the gate with no line-up and no rail work. That is returned as **text** by `rules.apha.zone_individual_work_note()` and rides on the class list as `procedure_note`, because none of it is data the app holds — what happened in the arena is not something to enforce, but the gate steward needs the rule in front of them before the class starts.
- `show_categories`: **what kind of show it is, and the judge panel it permits** (migration 124). APHA SC-100 and SC-105 name four — Single-Judge, Two-Judge, Paint-O-Rama, Zone Show — and each carries its own limit. Keyed on `show_types` like `judging_systems`, because which categories exist is the breed body's taxonomy; `show_type_id` NULL is a generic row. `shows.show_category_id` points here and `shows.offers_clinic` sits beside it. **`judge_limit_basis` is the load-bearing column**: `total` means the rule bounds how many judges the show may *have* (SC-105.D.2, SC-105.E.2) and the app can check it; `in_arena` means it bounds how many judge *at once* (SC-100.A, SC-105.C.1), which the app does not model, so the assignment count is only a reason to check the category. Chosen on the show details form and reported on the APHA readiness panel.
- **The APHA show number is the approval.** `GET /shows/{id}/apha-validation` reports SC-090 readiness — the application ladder, the class-list deadline, the reserved words in the show's name, and whether each assigned judge has APHA carding on file — and it treats a number on file as proof the show was approved, because APHA assigns one on approval and the results export already refuses without it. So the deadline ladder disappears the moment the number appears. The alternative was `apha_approval_status` / `_submitted_at` / `_notes` mirroring the AQHA columns, which would be the **third** association-prefixed pair on `shows`; migration 114 exists because of the second one. If that metadata is ever genuinely needed, the answer is a `show_approvals` table keyed on the (show, association) pair — not another four columns.
- **Everything SC-090 reports is a warning, bar one.** None of it is enforceable from here: the application goes to APHA on paper, the approved-judge list is APHA's, and the app cannot tell an APHA-sponsored show (entitled to "Championship" in its name) from any other. The single error is a show inside 30 days with no number, because SC-090.D.3 means it *cannot* be approved and that is not advice. Do not promote the rest to errors — an error nobody can clear is one the office learns to scroll past, which is the failure this panel exists to avoid. Equally, `APHA_JUDGE_NOT_CARDED` reads `judge_associations`, so it reports a gap in the app's **own records** and never claims a judge is unapproved; a carding typed in here does not make one approved either.
- **A judge limit is two different claims, and `show_categories.judge_limit_basis` says which.** SC-105.D.2 and SC-105.E.2 bound how many judges a Paint-O-Rama or Zone Show may *have*, so `APHA_CATEGORY_JUDGE_LIMIT_EXCEEDED` states the rule outright. SC-100.A and SC-105.C.1 bound how many may judge **"in the arena at any given time"** — concurrency the app has no model of — so a two-judge show rotating three judges is legal, and `APHA_CATEGORY_JUDGE_COUNT_UNEXPECTED` says in as many words that it is asking about the category rather than reporting a broken rule. Do not collapse the two into one "max judges" check: the app would then assert a rule it cannot see.
- **`shows.offers_clinic` earns its place by changing a check.** SC-105.C.3 lifts the SC-095 minimum class requirements for a two-judge show offered with a clinic, so `show_minimums()` returns `applies: false` with an `exempt_reason` naming the rule — kept separate from the judge count because "not required" and "under three judges" are different answers, and only one of them changes when a judge is added. It fires despite SC-095 biting only at 3+ judges precisely because of the concurrency reading above. Everything else the rules say about clinics (APHA-approved clinician, not alongside an approved Paint-O-Rama) is text on the panel.
- **The SC-100/SC-105 conditions the app cannot check are text, never findings.** Regional Club sponsorship, the per-year caps (two Paint-O-Ramas per club, four in Zone 10, one Zone Show per zone), clinician approval, SC-105.B's ten-judge combination ceiling — every one is a fact about APHA's whole calendar or a club registry this app does not hold. `category_requirements()` returns them against the chosen category and the panel prints them under **Not checked here**. A finding nobody can ever clear would train the office to scroll past the findings that matter.
- **SC-175.M.6 turned an inference into the rule's own structure.** `show_minimums` reads Junior/Senior halter out of class names and brackets, and that was inference when it was written. SC-175.M.6 gives the recommended halter classes as Weanling / Yearling / Two-year-old / Three-year-old / Four-year-old-and-older, **or combined as "2 and Under" and "3 and Over"** — exactly what the regexes already matched. Keep the citation: it is the difference between a heuristic somebody may delete and a reading of the rule book.
- **SC-095's minimum class requirements are reported, not judged.** A show with three or more judges must offer Open halter Junior (2 and under) and Senior (3 and over) plus four performance contests. The panel size is the only hard fact in that: **"Open division" is not a column** — the app holds a per-show discipline and a per-show bracket, and at a real Paint show the Open halter classes are bracketed by *age* ("Yearling", "Four Year & Older") while Amateur and Youth put their names in the bracket. So `show_minimums()` reads Open as the absence of another division's name, reads the age split out of the class name and bracket together, and hands back three lists — Junior, Senior, and the Open halter classes it **could not place** — for the panel to print. Only shortfalls that survive every reading are raised as findings, and the age-gap finding is suppressed entirely when anything is unplaced: a Grand & Reserve Champion class is Open halter with no age in it, and claiming a missing Junior class over a schedule that has one is how an office learns to stop reading the panel.
- **Performance contests are counted against SC-190.A's own list, in `PERFORMANCE_DISCIPLINES`.** Twenty disciplines behind the rule's twenty-eight entries (the Green variants collapse into their parents, as the classifier routes them), written as the names `rules/disciplines.py` produces so the two cannot drift. `performance_confirmed` is what the SC-095 requirement is judged on. `performance_upper_bound` — everything that is not halter — is kept beside it because the gap says how many classes were **not** matched, and therefore how much of the count rests on the classifier having routed them correctly. **What SC-190.A leaves out matters**: Showmanship, Longe Line, In-Hand Trail, the speed events and the equitation classes are not on it, so a schedule of nothing but barrel racing counts zero performance contests. Performance Halter and Halter — Group count as halter throughout.

## Entry rules (APHA)

- **APHA's entry limits are about the exhibitor's *other* entries, so they need the whole show.** `backend/apha_context.py` reads `apha_disciplines` (class → discipline) and `apha_entries` once per request and both entry doors pass it in the validation context; on the batch registration path it is built once and **appended to as the batch goes**, because six horses submitted together are still six horses and none are flushed yet. Three rules read it: SC-185.F caps an exhibitor at five horses across the individual working events, SC-185.F.1 at two in Longe Line and two in In-Hand Trail, and AM-300.H stops two Amateur Walk-Trot exhibitors sharing one horse in one event — the last being per *horse* and across exhibitors, where the others are per exhibitor. The caps count **distinct horses, not entries** (six classes on one horse is one horse) and run **before the division is looked at**, since SC-185.F applies whether somebody is riding Open or Youth. **No context means no cap**: a non-APHA show builds no discipline map, and refusing an entry on a guessed discipline would be worse than not checking.
- `entry_attestations`: **what the entrant declared about an entry, recorded rather than verified** (migration 118). APHA's Novice divisions are gated on points and prize money the app does not hold and never will — AM-205 decides Novice Amateur per category at the time status is applied for, YP-255.A.1 caps Novice Youth fence-work earnings at $750 — and the rule book puts the responsibility on the exhibitor and the burden of proof on whoever protests. So the app makes somebody say it and records who, when, and the exact words. **`statement` is a stored copy, never a pointer**, because APHA revises its limits and a pointer would silently restate what somebody agreed to two seasons ago — the same reason a signed waiver keeps its own text. The wording comes from `ATTESTATION_STATEMENTS` in `rules/apha.py` via `backend/attestations.py` and is **never accepted from the client**: a caller able to compose the sentence it is attesting to could attest to anything, which is the paperwork-verification rule applied to a fact that has nothing on file to derive it from. Rows are assigned to `entry.attestations` *before* validation and before commit, so the rules engine reads the declaration off an unflushed entry — a check that queried the database would reject every new Novice entry.
- **There is no division picker, because the class is the answer.** `rules.apha.divisions_for_bracket` reads the division off the class's bracket (falling back to its name), and **every bracket it matches resolves to exactly one division** -- so the exhibitor picks a class and a horse, and nothing else. Before this, all nine were offered on every class and "56 - Youth WT Showmanship 5-10" could be entered as Amateur, which nothing downstream would catch: `apha_division` is stored data and every rule that reads it takes the entry at its word. The Novice divisions are not a sub-choice inside an Amateur class -- a show that offers them runs them as their own classes, bracketed "Novice Amateur" and "Novice Youth" -- so a bracket reading plainly "Amateur" resolves to AMATEUR alone.
- **A bracket that says nothing files no division at all, and that is not a gap to close.** "Yearling Stallions" is almost always an Open halter class; filing it as OPEN would be right most of the time and wrong the rest -- a youth or amateur entry in a class the show ran for everyone, filed under a division nobody chose, on the entry APHA reads. `validate_entry` returns early on a division-less entry by design, which is what every entry did before the picker existed. The **desk** has no picker either: the division was chosen when the class was built, so `rules.apha.division_for_class` is both what `POST .../entries` fills in and what the desk prints beside its class picker (`apha_division` on the desk's class payload), and its Novice check reads it. A value on the request still wins, for an API caller with a reason.
- **Solid Paint-Bred is a registry, not a division, and nothing refuses a Solid Paint-Bred horse.** SC-325, amended in 2024, ended the separate Solid Paint-Bred showing divisions on 1 January 2025: both registries compete and are awarded together. So there is no check keeping one out of Open, no bracket resolves to `SOLID_PAINT_BRED`, and `horses.is_solid_paint_bred` is a fact on the horse's card that decides nothing about an entry. The value stays in `DIVISIONS`, the CHECK and the labels **only so entries made before 2025 still read** -- dropping it would need a migration that fails on those rows. Do not reinstate the Open-class block from an older rule book.
- **The Novice divisions carry no ownership requirement.** AM-210 dropped it for Novice Amateur from 2025 and YP-205 for Novice Youth from 2026, so `RELATIONSHIP_REQUIRED_DIVISIONS` is Amateur, Amateur Walk-Trot and the three Youth divisions. APHA-sponsored shows such as the World Show still ask, but the app cannot tell a sponsored show from any other, and refusing every Novice entry on a borrowed horse everywhere to catch that one show is backwards. A relationship the exhibitor has stated is still copied onto the entry. And **YP-075-1 (2026) asks for the three 13 & Under classes only at a show with three or more judges** -- `_check_youth_thirteen_and_under` counts the assigned panel the way SC-095's minimums do.
- **`youth_age()` is not `horse_calendar_age()`, and mixing them costs a year.** YP-075 sets a youth exhibitor's division by their age **on 1 January**. The horse helper subtracts calendar years because every horse has a January 1 birthday; a person does not, so somebody born in June 2008 is seventeen on 1 January 2026 — and subtracting years would call them eighteen and refuse a youth entry the rule allows. The two are tested against the same date side by side so the distinction cannot quietly collapse. (AQHA's `_calendar_year_age` is used for both horses and youth in `rules/aqha.py`; whether that is right depends on AQHA's own wording, which has not been supplied.)
- **A youth age cap only ever tightens.** The cap comes from `entries.apha_division` — stored data, and `YOUTH_WALK_TROT_5_10` / `_11_18` state their range in the value — and a class bracket saying "13 & Under" narrows it further. It never widens and there is **no lower bound**, because YP-075.A.1 explicitly lets a 13-and-under exhibitor "choose which division to compete on a per class basis". The bracket reaches the rules engine through `apha_brackets` on the shared context, not `Class.division`, which is not eager-loaded at either entry door.
- **Everything AM-250 produces is a warning, and that is the rule rather than caution.** AM-250.A sorts the performance classes into twenty-five categories approved for Novice Amateur points and awards — but it governs *points*, not eligibility. A Novice Amateur may enter Longe Line; what they will not do is earn anything for it. Refusing the entry would invent a restriction the rule does not impose. Categories **XV and XXI are deliberately absent from the map**: both are marked "class no longer offered", and listing them would let a show award points in a class APHA has retired. The category matters beyond this check — AM-205 decides Novice status *per category*, which is what the `entry_attestations` declaration is about.
- **SC-190.A.3.a is an error, and it is the only APHA entry rule here that refuses on the horse itself.** Three years old or older for English Versatility Pattern, Western Versatility Pattern and the ranch events SC-190.A names. A missing Coggins can be produced and a membership bought at the desk, but a two-year-old cannot become three — the entry is ineligible in a way nothing at the show can fix. It declines to run with no foaling date and with no discipline map, the same two outs the SC-185.F caps take. **"Ranch classes" is read as the ranch events SC-190.A enumerates and no wider**: the classifier knows a dozen disciplines starting with "Ranch", and Ranch Conformation is a halter class. Age is counted in show years through `horse_calendar_age` — every horse has a January 1 birthday — mirroring AQHA's `_calendar_year_age` so the two cannot disagree about a December foal.

## Judging and results filing (APHA)

- **SC-215.E.3's symbol system is guidance, not a `judging_systems` row.** The judge watches the round and picks a number inside a band, so there are no maneuvers to add up and nothing for a card to total; forcing it into that table would mean inventing a maneuver range for a system that has none. Seven bands live in `rules/apha.py` beside the zone notes, served by `GET /judging-systems/symbol-system`. A class scored this way carries **no** judging system, which is what the app already did by default. The bands stop at ten because below that is an elimination rather than a score, and scope is Working Hunter only — SC-215's section heading was never supplied, so it is read from the rule's own words.
- **SC-125's results format is delegated, not missing.** SC-125.A specifies "electronic results (in the format specified by the APHA Performance Department)" — the rule book points elsewhere rather than defining a layout. So the Show Results report's columns will not be settled by reading more rules, and the caveat on that page stays until something from the Performance Department replaces it. Do not quietly drop it on the grounds that SC-125 has now been read.
- **The results deadline is a calendar, never an accusation.** `results_window()` counts SC-125.A's ten days from the show's last day and its thirty-day delinquency mark, and is None until the show has ended. `APHA_RESULTS_OVERDUE` and `APHA_RESULTS_DELINQUENT` say the date has gone by — **the app cannot see a postmark**, and both messages say so, because a warning that reads as an accusation to an office that filed on day nine is one they learn to dismiss along with everything beside it.

## The class-code catalog

- `association_standard_classes`: **the associations' approved class codes** — a view over `association_standard_class_versions`, keyed on the `show_types` row whose catalog it is (migration 114). Replaces `apha_standard_classes` and `aqha_standard_classes`, which were the same table twice with no room for ApHC or FQHR. `show_type_id` rather than `association_id` on purpose: a class *code* is the breed body's catalog identifier, which is the question `class_associations` and `standard_classes` already answer against `show_types`. **Type 2**, because the associations reissue the list every year and a show run in 2026 under a code retired in 2027 still has to render its own program — so a changed name closes its version (`inactive_date`) and opens a new one, a retirement only closes, and nothing is ever updated in place or deleted. A partial unique index on `(show_type_id, code) WHERE inactive_date IS NULL` is what makes it a Type 2 rather than an append-only log. **Read the view, never the versions table** — `backend/standard_classes.py` is the one place that does. Loaded by admins at `/admin/standard-classes`; `association_class_imports` records each upload.
- **A class-code catalog is loaded, never edited.** `/admin/standard-classes` takes the association's own published file and diffs it; there is no screen for typing a class code in by hand. The rows go out on entry forms and into association reporting under that association's identifier, so the file they publish is the only authority for what is in the list — a hand-typed correction is a local invention that the next upload silently reverts.
- **Preview and apply both parse the file; nothing is parked between them.** `apply` takes the same upload back rather than reading a staged copy, so there is no half-finished import to expire and the diff being applied is recomputed from the same bytes the admin approved. It also re-diffs, and 409s if a code the admin ticked for retirement is no longer missing — the catalog moved underneath them, so the list on screen is not the list they were approving.
- **A code missing from the file is not automatically retired.** The importer flags it and the admin ticks it. This year's approved list is not a statement that last year's codes never existed, and a show that ran classes under one still has to render its own program. Retiring only ever closes the version — the row stays readable through `association_standard_class_versions`.
- **The catalog rows have been hand-tidied, and re-uploading the same file undoes that.** The 634 APHA rows loaded before this feature normalise `(Zone 12, 13, 14 only)` to `(Zone 12-14)` and fix APHA's own `Performace Halter` typo. Uploading the 2026 PDF reports 28 changes, every one of them a cleanup being reverted to what the association actually printed. That is why the preview shows before-and-after per row rather than a count: the admin has to be able to see that a "change" is the file being less tidy than the catalog, and simply not apply it.
- **`Base.metadata.remove()` keeps the view out of `create_all`.** `AssociationStandardClass` maps the `association_standard_classes` VIEW. Startup runs `Base.metadata.create_all`, and on a database where migration 114 has not run that would create a *table* under the view's name, after which the migration's `CREATE VIEW` fails. Dropping the Table from the metadata takes it out of `create_all` entirely; the mapper holds its own reference, so queries are unaffected. `has_table()` returns True for a view, so an already-migrated database was never at risk — the un-migrated one was.
- **Migration 114 states its defaults separately from its `CREATE TABLE`, and this is why.** `create_all` had already made both new tables from the models before the migration ran, so `CREATE TABLE IF NOT EXISTS` skipped — leaving tables whose `id` has no `DEFAULT`, because the model's `default=uuid.uuid4` is applied in Python. The first attempt failed on a not-null `id`. Any migration adding a table that also exists as a model has to assume startup got there first: state the server defaults and SQL-only CHECKs in their own statements, and have inserts supply their own ids.
