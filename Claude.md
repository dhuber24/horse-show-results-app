# Claude.md - Horse Show Results App

This is the short orientation guide for AI-assisted development in this repo. Use it as the map, then open the focused docs linked below when a task touches that subsystem.

## Project Purpose

Horse Show Results is a browser-based app for ranch and western pleasure horse shows.

It does:

- Let exhibitors and office staff manage class entries.
- Assign show-level back numbers.
- Let authorized scribes manually enter placings.
- Publish results live.
- Track horses, exhibitors, show staff, documents, and association registration data.
- Provide limited association compliance validation where the app stores enough data, including AQHA class-code, registration, membership-number, workshop-date, and age checks.

It does not:

- Judge classes.
- Score maneuvers.
- Calculate penalties.
- Enforce association judging rules or replace official association review.

Placings entered by authorized staff are treated as final published results, with audit history for changes.

## Roles

- `ADMIN`: full access.
- `SHOW_MANAGER`: requests and manages hosted shows; can assign staff for their shows. Whoever creates a show gets the `show_managers` row automatically; a co-manager is added in setup Step 1 (`POST /shows/{id}/managers`). Removing the **last** manager returns 409 — that row is the only way a manager reaches the show.
- `SHOW_SECRETARY`: manages assigned shows, classes, entries, back numbers, and results administration. With `SHOW_MANAGER` and `ADMIN`, also works the counter at `/admin/shows/[id]/desk` — back numbers, class entries, side pot buy-ins, signing off on registration papers and membership cards physically inspected, and creating horses for exhibitors on that show's roster.
- `SCRIBE`: enters placings and scores for assigned shows. Named for the show-world role — the person at the judge's shoulder who records what the judge calls. Renamed from `SCOREKEEPER` in migration 093; see the Sharp Edge on why this is not "Ring Steward".
- `GATE_STEWARD`: runs the warm-up side of the in-gate for assigned shows via `/gate` — per-class order-of-go (`entries.gate_order`), exhibitor check-in (`entries.gate_checked_in`), and class gate progression (`classes.gate_status`: pending/ready/in_progress/done; ready is auto-set when everyone is checked in, in_progress is set by the steward when the first exhibitor enters the ring, and on-deck is derived per ring: each ring's first not-yet-started class of the day; exhibitor check-in is only open for on-deck classes, enforced server-side). The gate screen is scoped to one show day and is also accessible to ADMIN / SHOW_MANAGER / SHOW_SECRETARY. Only one class per ring may be in progress; starting a class while another runs in the same ring returns 409 and the UI asks whether the previous class finished (yes marks it done). Classes without a ring default to the show's first ring (a "Ring 1" is auto-created when the show has none). Mistake recovery: per-entry check-in undo, undo-start (in_progress → ready), reopen (done → in_progress), and a full class reset endpoint that clears all check-ins. Assigned/invited in setup Step 1 like scribes.
- `EXHIBITOR`: views own entries/results, manages profile/horses, and self-registers for any `PUBLISHED` show (picks classes + horses; secretary handles back numbers and any late-add entries after the show goes `ACTIVE`).
- `TRAINER`: manages a linked trainer registry profile used on horse records.

New Show Secretary, Show Manager, Trainer, and Exhibitor registrations are currently auto-approved. The `users.is_approved` column remains as an account lock gate. Show Managers create shows directly via `/admin/shows/new`; there is no per-show approval gate.

## Core Data Concepts

- `shows`: event shell with venue, dates, primary association, status, optional APHA show number, AQHA approval metadata, `office_charge_cents` + `office_charge_basis` (`per_back_number` default, or `per_horse`), and `shavings_ban_outside` policy bool. Office charge and the policy bool surface on the exhibitor self-registration screen. Since migration 097 it also states **which health papers it requires** — `requires_coggins` (default true), `requires_health_certificate` + `health_certificate_valid_days` (default 30), `requires_vaccination` + `vaccination_valid_days` (default 365) + `vaccination_notes`. Set at `/admin/shows/[id]/desk/paperwork` — a registration question, not a setup one.
- `associations`: **the registry of bodies a horse or person is affiliated with**, typed `breed` (AQHA, APHA, ApHC, FQHR) or `club` (NSBA, WSCA, MNSPHC) — migration 080, MNSPHC added in 105. Everything that stores a registration or membership number points here: `horse_registrations`, `exhibitor_registrations`, `trainer_registrations`, `exhibitor_documents`, `show_secretary_certifications`. This is **not** the same concept as `show_types`: a show type is show configuration ("what kind of show is this?"), while an association is a property of the horse or person ("this horse is registered with AQHA"). The same code appears in both lists on purpose. There is no `associations` row for OPEN — Open means *no* breed association.
- `show_sanctioning`: per-show club sanctioning overlay set in setup Step 3 — `show_sanctioning(show_id, association_id, per_class_fee_cents)` referencing club rows in `associations`. Admins manage the registry; non-admin wizard users may submit `sanctioned_association_requests` for admin review. Show setup asks for a breed association (or Open) as the show type, then optional club sanctioning.
- `disciplines`: per-show **riding styles** (Halter, Western Pleasure, Trail, Barrels). Each carries `default_score_type` (`placement` / `pattern` / `time`) that new classes inherit when score_type is omitted. Renamed from `divisions` in migration 074.
- `divisions`: per-show **age/skill brackets** (10 & Under, Walk-Trot, Amateur, Youth 14-18). Each division belongs to one or more disciplines via `discipline_divisions` (M2M). A division with no discipline memberships is unusable on classes. Renamed from `sections` in migration 074.
- `discipline_divisions`: join table on `(discipline_id, division_id)`. A `(discipline_id, division_id)` pair on a class must exist as a row here — enforced by a Postgres composite FK on `classes`. The single-class create endpoint (`POST /shows/{id}/classes`) upserts the membership on demand, so any valid in-show pair is accepted; the update path still 422s on an unregistered pair.
- `standard_disciplines` / `standard_divisions` / `standard_discipline_divisions`: curated lookup lists for the setup picker; `show_type_id NULL` is the generic fallback. The OPEN class wizard fetches the AQHA + APHA shared universe and merges by name for its standard library.
- `standard_classes`: canonical per-show-type class catalog (migration 068) backing the Matrix setup picker on `/admin/shows/[id]/setup`. Each row pairs a class to a `(standard_division, standard_section)` cell via composite FK to `standard_division_sections`. AQHA is fully seeded (~1589 classes from the 2026 Class Master Listing) via `scripts/generate_aqha_standard_library_seed.py` — re-run after `database/seeds/aqha_standard_classes.csv` changes. APHA/NSBA/WSCA/ApHC seeding is upcoming Phase 2/3 work.
- `classes`: competition classes, sorted by `sort_order`. **Both** `division_id` (discipline) and `section_id` (bracket) are required (migration 061). `score_type` is `placement` (judges rank — rail/halter), `pattern` (judges score numerically — showmanship/horsemanship/etc.), or `time` (clocked event); derived from `division.default_score_type` at create time when omitted. `entry_fee_cents` is informational and surfaced on the exhibitor self-registration screen — the app does not collect payment. APHA/AQHA catalog imports auto-route class names through `backend/rules/disciplines.py`, create any missing divisions/sections, and register the (div, sec) membership. The Standard Library picker (any show type) lets the secretary check `(discipline × bracket)` cells from `standard_divisions` / `standard_sections` and commit them in one click via `POST /shows/{id}/classes/from-library`. Schedule-builder picks with no section use the per-show "Unassigned" section placeholder.
- `judges` / `judge_associations` / `show_judges`: the judge registry (migration 085). `judges` is the person — name, email, phone, identified by name + email; `judge_associations` is what they are carded with, pointing at `associations` (not `show_types`); `show_judges` is only the assignment of a registry judge to a show plus `sort_order`. Show setup **picks** a judge and displays their details read-only; corrections are made on the registry (admin-only `PATCH /judges/{id}`) so one fix reaches every show that judge works.
- `class_associations`: association-specific codes for a class, useful for dual-sanctioned shows.
- `aqha_standard_classes`: official AQHA class-code lookup used by the AQHA picker and validation.
- `entries`: class-level exhibitor/horse registrations.
- `show_entries`: show-level exhibitor record — back number, plus show sign-up (migration 088). Since migration 104 it also carries `preferred_back_number`, the number the exhibitor **asked for** on the class registration screen, as against `back_number`, the number the show **issued**. `registered_at` set means the exhibitor completed sign-up; NULL means it is a shell row a secretary created while adding a late entry by hand. **Class self-registration requires a completed sign-up** and returns `409 SHOW_SIGNUP_REQUIRED` otherwise.
- `show_fees`: the show's non-class fee catalog (stalls, shavings, camping, late/post entry, surcharges), each with an `amount_cents` and a `unit`. A reservable fee may also carry an **early-bird rate** — `early_amount_cents` + `early_deadline` (migration 092), a pair that only counts when both are set. `amount_cents` is always the standard, post-deadline rate. Staff set it in setup Step 4 and on `/admin/shows/[id]/fees/boarding`.
- `show_payments`: what the office **recorded collecting** against an exhibitor's account at one show (migration 096) — amount, method, reference, the day it was received, and who took it. Scoped to `show_entries`, not to an individual charge: the desk takes one check for the whole bill. `amount_cents` is signed, so a refund is a negative row. **Recording, not processing** — no card is handled and no processor is called. This is the half that makes `billed − paid = balance` mean anything; without it an outstanding balance is the full bill for everyone, forever. Read through `billing.build_account` / `summarize_accounts`. `/admin/shows/[id]/financials` is the summary — headline money figures and side pots only, since registration counts and revenue-by-category are reports; per-exhibitor accounts and payment entry live on `/financials/exhibitors`, reports on `/financials/reports`, both reached from buttons on the summary. Both screens self-refresh (`AutoRefresh`) so a totals board left open at the desk does not silently go stale while a second staff member takes money.
- `show_entry_reservations`: how many of each `show_fees` row an exhibitor booked at sign-up (stalls, bags of shavings, camping nights). Points at the fee catalog rather than restating those as columns; which fees are reservable is derived from the fee's `unit` (`per_stall` / `per_bag` / `per_night` / `per_show`), so a show's own custom per-stall fee is offered with no code change. `reserved_at` is the day the line was booked and is what selects between the fee's two rates.
- `horse_access_requests`: consent, pending, for a horse changing hands (migration 087). `kind='link'` is someone asking the owner to put their horse on that person's profile; `kind='transfer'` is the owner handing ownership over, which the recipient must accept. `approver_exhibitor_id` is always whoever must press the button, so approve/decline is one code path. The token is emailed **and** shown for copy/paste — see the mailer note in Sharp Edges.
- `results`: placings, **one card per judge** — `judge_id` points at `show_judges` (the assignment, not the registry judge) since migration 095, and NULL means unattributed. For `pattern`/`time` classes, `raw_score` is the source of truth and `place` is recomputed server-side on every change, ranked *within each judge's card*. Visibility is gated by `classes.results_published_at` — see below.
- `classes.results_published_at`: the **publish gate** (migration 094). NULL means the class's placings are a staff-only draft; a timestamp means they are on the public `/live` and `/results` screens. The scribe screens autosave continuously into the draft and a human posts the class with one button. Reads split on it: `GET /shows/{id}/classes/{cid}/results/` returns everything to show staff and `[]` to everyone else, and `GET /shows/{id}/results-index` (public, no caller to except) filters on it outright.
- `result_audit`: placing change history (placement classes only — derived placings are not audited, and **only once the class is published**).
- `coggins_override_audit`: **historical** (migration 082). One row per effective show-staff bypass of the Coggins entry gate, back when health paperwork blocked an entry. Nothing writes it now — an override needs a block to override — but the rows stay readable at `GET /shows/{id}/coggins-overrides`. Health shortfalls are a flag now, not a stop: see `show_health_flags` below.
- **The registration desk** (`GET /shows/{id}/desk`): not a table. Everything the show office does to one exhibitor, in one read — back number, class entries, side pot memberships, paperwork checks, and their balance. Entries, back numbers, and check-in were three screens and are one conversation at the counter; `/admin/shows/[id]/entries`, `/back-numbers`, and `/check-in` all redirect to `/admin/shows/[id]/desk`. **The desk computes nothing of its own**: money comes from `_load_financials` → `build_account`, paperwork from `build_verification_checklist`, and every button posts to the endpoint that already owned that job. The one write it adds is `POST /shows/{id}/desk/exhibitors`, which creates the `show_entries` shell row those endpoints assume — a back number and a pot entry both hang off it, so before this a walk-up could not be given either without first inventing a class entry for them.
- **Health flags** (`GET /shows/{id}/health-flags`, and inline on the desk): not a table. Which entered horses have health paperwork that will not carry them through the show, derived on read from `horse_documents` and judged against `shows.end_date`. Covers **the documents this show requires** — Coggins, CVI, and vaccinations — never all three unconditionally. Computed rather than stored so it clears itself when the exhibitor uploads a current document; there is no row to remember to close. One implementation in `backend/routers/horse_documents.py` (`health_by_horse` / `document_health` / `health_requirements`), shared by the desk, the flag endpoint, and the exhibitor's registration screen so they cannot disagree about a horse.
- `show_verifications`: what the show office **physically inspected** at the desk (migrations 090, 098). One table, four `kind`s — `horse_age` (foaling date on the papers), `horse_registration` (a registration number, per association), `exhibitor_membership` (a membership card, per association), `horse_health_document` (a Coggins, CVI, or vaccination record, keyed on `(horse_id, document_type)`) — because the actor, the question, and the staleness rule are identical. A `trainer_membership` kind existed briefly (migration 098, reversed by 100): the trainer is not at the counter, has no entry and no back number, and their card is the association's business rather than this show's, so the check sat permanently unverified and inflated every outstanding count. Per show on purpose: this is a show attesting its own office saw the paper, not a permanent property of the horse or person. `verified_value` snapshots what was on file at sign-off, so a later edit flips the check to stale instead of leaving it green; for a health document that snapshot is the standing derived **from the documents on file** (`valid:2027-05-03`, or `missing:none` when the office signed off on paper the app has never seen). A health sign-off may also carry `attested_expiry` (migration 101) — the date staff read off the paper in their hand, which clears the horse's health flag when it covers the show. Records only; nothing here gates entry.
- `show_waivers` / `show_waiver_signatures`: the entry blank, the liability release, and venue rules (migration 099). Free text, because the words come from the venue's insurer or the fair board and this app has no business supplying them; `is_required` separates what an exhibitor cannot compete without from what the show wants read but does not chase. Signatures arrive by two routes into **one** table — the exhibitor types their name at sign-up, or hands a paper blank across the counter and staff record it with `on_paper` set — so a show running entirely on clipboards still has a working outstanding count. `signed_by_guardian` + `guardian_relationship` because a release signed by a twelve-year-old is not a release and youth classes are a third of a schedule. Emergency contacts get no table here: `exhibitors` has carried `emergency_contact_name`/`_phone` since migration 041, and the desk reads **and writes** those columns directly via `PATCH /shows/{id}/exhibitors/{exhibitor_id}/emergency-contact`.
- `show_contact_messages`: the show's inbox (migration 091). Anyone — including visitors with no account — can message a show from its page; staff read it at `/admin/shows/[id]/messages`. **Stored, never emailed**: `mailer.py` does nothing without SMTP, and a forward-only contact form would accept a message, say "sent", and lose it. Every sender field the writer *types* is self-reported and joined to nothing. Since migration 103 a message sent by a signed-in caller also carries `sender_user_id` / `sender_exhibitor_id`, **stamped from the session and never from the body**, and the inbox badges it with that person's back number at this show. That is the whole point of the addition: a secretary reading a name in a free-text field cannot tell the exhibitor holding number 42 from somebody who has never been to the show, and the answer to the question usually depends on which it is. Being signed in does not gate sending — a stranger asking about stalls is still the case the endpoint was built for, and an anonymous message is a NULL stamp rather than a rejection.
- `document_extractions`: one row per AI read of an uploaded horse document (migration 083) — what the model suggested (`extracted`), what the human saved (`accepted`), and which suggestions they changed (`overridden_fields`). Written *before* the document is saved and linked to it on save, in the same transaction. `horse_id` is nullable (migration 084) because the add-a-horse wizard reads documents before the horse exists; it is attached on save. See `docs/document-extraction.md`.
- `futurities` / `futurity_fee_tiers` / `futurity_classes` / `futurity_divisions` / `futurity_division_classes` / `futurity_entries`: a futurity programme within a show (migration 107). It was a single `show_fees` row with code `futurity` — one flat per-entry amount next to the jackpot fee — and that cannot describe one. A real futurity prices the same class **three ways depending on how the horse got there** ($75 / $100 / $150), closes entries on a stated date after which every class carries a late fee, charges an office fee per horse that depends on club membership, and hands out **Hi-Point awards** over a named subset of its classes. Shaped after `side_pots`, with two differences. **An entry is an enrollment of a horse, not a bet on classes** — the futurity's classes are ordinary `classes` entered through ordinary `entries`, and the money is derived by `billing.futurity_charge_cents` as *tier × classes entered + office fee + late fee × classes*. **The futurity supplies the class price**, so a futurity class carries `entry_fee_cents = 0`; pricing one double-charges, and the UI warns rather than silently zeroing it (the fix belongs on the class). `futurity_entries.entered_at` is stored and never `now()` — same rule as `reserved_at`. Reached from the **Futurities** tile on the show dashboard; exhibitors enter through `/shows/[id]/register`.
- `side_pots` / `side_pot_classes` / `side_pot_entries` / `side_pot_payouts`: optional money pool spanning multiple classes; one **side pot entry** per exhibitor (the UI's name for it — staff enter a pot, and `entry_fee_cents` is surfaced as the **buy-in** so it doesn't read as the class fee), payouts written on settle. Entries are added by picking from the show roster (`GET .../side-pots/{potId}/roster` → `show_entry_id`), never by typing a back number. **`paid` defaults to true and the UI never asks**: pot money settles with the exhibitor's show bill at the end of the show, so being in the pot is what owing the buy-in means — a pot whose rows all read unpaid has a $0 pool and pays out nothing. The column, the standings "Unpaid" flag, and `PATCH .../entries/{id}` stay for pots that tracked it the old way. Reached from the **Side Pots** tile on the show dashboard — a side pot is desk money and live standings, not part of the published fee schedule, and the tile's old home on `/admin/shows/[id]/fees` was orphaned by the setup-wizard rebuild. `/admin/shows/[id]/side-pots/[potId]` is a hub — pool figures plus buttons to Settings, Side Pot Entries, and Standings; **Settle lives on Standings**, next to the table it freezes.
- `users`: login accounts and roles. First/last name are the editable source of truth; `full_name` is a derived display compatibility field. Since migration 102 a user may also set **one self-written security question** — `security_question` + `security_answer_hash` (a pair, enforced by CHECK), plus `security_answer_failed_attempts` / `security_answer_locked_until`, which close the *reset route* for 15 minutes after 5 wrong answers and are cleared by a successful login. This is what makes `/forgot-password` mean forgot: the old flow proved identity with the current password, which the person who needs it does not have. Email would be the ordinary answer and `mailer.py` does nothing without SMTP, so a mailed token would accept the request and lose it. See `docs/auth.md`.
- `exhibitors`: person/profile records, optionally linked to users.
- `horses`: horse records with owner/trainer text, free-text `sire_name`/`dam_name` pedigree (migration 079), breed/color, registrations, documents, and APHA SPB flag. `name` is the **registered (association) name** and is required — it is what the horse is entered and published under; `barn_name` is the optional stable/call name (migration 081). Owner + sire + dam are the program columns shown on the public class schedule and the admin entry list.
- `exhibitor_registrations`: exhibitor membership numbers per association.
- `backend/rules`: association-specific validation hooks; AQHA currently enforces the first practical validation slice.
- `users.aqha_management_workshop_completed_at`: AQHA show-management workshop date used to validate assigned managers/secretaries.
- `trainers`: trainer registry; first/last name mirror the linked user when present, and derived `name` remains for trainer-list display. Carries private contact, public ad-ready profile (`business_name`, location, `website`, `bio`, socials, `is_public`), compliance dates (`safesport_completed_at`, `background_check_expires_at`), and a self-attested `has_liability_insurance` flag.
- `trainer_registrations`: per-association trainer membership with `status` (`professional`/`non_pro`/`general`) and optional `expires_at`. Mirrors `exhibitor_registrations`.
- `trainer_documents`: trainer-uploaded images stored as BYTEA. Currently restricted to one `HEADSHOT` per trainer.

## Common Feature Recipe

Most data-backed enhancements follow this path:

1. Add a SQL migration in `database/migrations/`.
2. Update `backend/models.py`.
3. Update `backend/schemas.py`.
4. Update or add a FastAPI router in `backend/routers/`.
5. Update or add a Next route handler in `frontend/app/api/`.
6. Update the relevant page/form/component in `frontend/app/` or `frontend/components/`.
7. Run focused validation.

Start the app:

```bash
docker-compose up
```

Run frontend checks from `frontend/`:

```bash
npm run type-check
npm run lint
npm test
npm run build
```

Run backend tests. **These must run in Docker** — the host interpreter is Python 3.9 and the backend

byte-compiles without executing, which is why the compile check alone never caught this:

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd)/backend:/app" -w /app \
  horse-show-results-app-backend:latest python -m pytest
```

Run everything (backend tests in Docker, then the frontend checks) from repo root:

```bash
bash RUN_TESTS.sh
```

```powershell
powershell -ExecutionPolicy Bypass -File database/migrate.ps1
```

Run the documentation guard manually:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/check-docs-updated.ps1
```

## Project Conventions

- Prefer existing router, schema, and component patterns over new abstractions.
- Keep migrations append-only once applied.
- Use `safe_uuid()` for untrusted UUID strings in backend code.
- Use `selectinload` for relationships needed by Pydantic serialization; avoid lazy-load surprises in async routes.
- **`db.get(Model, id, options=[selectinload(...)])` silently drops the options when that row is already in the session's identity map** — the common case right after you created or fetched it. The relationship comes back unloaded, the first attribute read is lazy IO in an async request, and SQLAlchemy raises `MissingGreenlet`: a 500 with an empty body, on a request whose write already committed. Re-read with `select(Model).where(...).options(...).execution_options(populate_existing=True)` instead. This is what broke side pot creation.
- Authenticated frontend mutations should usually go through `frontend/app/api/` route handlers.
- Route handlers should preserve backend status codes and use `safeFetchBackend()` when `204` responses are possible.
- Never call `res.json()` on a backend response unguarded — a 500 comes back as plain text and the throw hides the real error behind an opaque parse error. Route handlers use `safeFetchBackend()`; server components use `readJsonBody()`. See `docs/frontend.md`.
- Admin pages use `Breadcrumbs`.
- Destructive UI actions use inline confirmation, not modal overlays.
- Disabled buttons should include a `title` explaining why they are disabled.
- The pre-commit documentation guard blocks staged implementation changes unless related docs are staged too. Bypass once with `DOCS_CHECK_BYPASS=1` only for changes with no documentation impact.

## Sharp Edges

- **A setup step is a position in a flow, not a folder.** Four of the six live under `/setup`; Step 1 is `/admin/shows/[id]/edit` and Step 6 is `/admin/shows/[id]/classes`, because both were screens before the wizard and are deep-linked from elsewhere. `StepLayout` is what makes a route a step. Moving those two under `/setup/` to tidy the tree would break every existing link and buy nothing. The reverse also holds: `/setup/paperwork` exists as a redirect only — paperwork is a registration question and lives at `/admin/shows/[id]/desk/paperwork`.
- Document extraction only ever *suggests*. Nothing read off a scan reaches `horse_documents` without a human pressing save — `horse_documents.expiry_date` is what the health flags are computed from, so a misread date would quietly clear a horse the office should have been chasing. The upload form's auto-upload-when-complete shortcut is deliberately suppressed once a document has been read.
- **Health paperwork does not gate entry.** A missing, undated, or lapsed Coggins used to 422 on both entry paths; it now flags. Refusing the entry never made a horse compliant — it just moved the discovery to the desk and turned the office's to-do into an "override" that recorded a bypass. Do not re-add the block.
- **The flag and the sign-off answer different questions.** An earlier version of this file argued there was no point signing off a Coggins, on the grounds that it is either current (the file says so) or lapsed (signing changes nothing). That collapses two questions. The file answers *is the date still good*. Only a person at the counter answers *does this paper describe this horse* — markings and description against the animal in the trailer, on a document that is genuine and physically present. So a health line carries both: a derived `status` and an attested `inspection`, and they can disagree in both directions. A current Coggins nobody has looked at and a lapsed one the office is holding are different situations.
- **An inspection clears the flag only when it records a date.** `attested_expiry` is what staff read off the paper; given, and covering the show, `attested_health()` overlays the derived standing so the horse reads `valid` and drops off the chase list. Left blank the inspection is still recorded and the horse stays flagged — "I looked at this" and "this is valid" are different claims, and one click clearing a flag on a test that expired in 2019 is the same conflation the sign-off exists to undo, run backwards. Anything reading `valid` this way is marked `attested: true`, because the app is not holding that document and the *next* show will ask again.
- **The attestation is an overlay, never an input to the snapshot.** `document_health()` carries `file_snapshot` — the standing derived from the documents alone — and `health_snapshot()` returns that. Snapshotting the overlaid value would have the sign-off recording its own effect, and the check would read back `stale` the instant it was written. Staleness has to keep meaning "the file changed under me".
- **A health sign-off must work with nothing on file.** `horse_health_document` is keyed on `(horse_id, document_type)`, not on a `horse_documents` row, because the ordinary case at a horse show is an exhibitor handing over a paper the app has never seen. Requiring an upload would break the sign-off exactly where it is needed. `missing:none` is a perfectly good thing to have attested to, and it goes stale the moment a document arrives — which is correct.
- **Coggins is universal; CVI and vaccinations are not.** A Certificate of Veterinary Inspection follows from crossing a state line and vaccination rules come from the venue, so both are opt-in per show (migration 097). Deriving a flat "no CVI on file" flag would light up every in-state horse at every show and staff would learn to ignore the whole panel — the second feature would poison the first. The policy has to exist before the derivation is worth having.
- **Coggins carries its own expiry; the others are dated from issue.** `HealthRequirement.valid_days` is None for Coggins on purpose — how long a negative test stays good is a state rule (twelve months in most, six in some) and the app does not know which state the horse is standing in. A CVI is written as "issued within 30 days", so `effective_expiry()` counts the show's window from `issue_date` — but a printed expiry on the document always wins.
- **A signature is the one value the backend does not derive.** Every other sign-off reads its value off the record precisely so a caller cannot attest to something nobody has on file. There is nothing to read a signature from, so `signed_name` is accepted from the client — and staff typing a name off a paper blank is a feature, not a hole. `on_paper` is still set by the endpoint, not the caller, so the two routes stay honest about which one a row came through.
- **One exhibitor may show two horses in the same `pattern` class, and only there.** A pattern class is judged run by run — showmanship on two horses is two runs, two scores, and two entry fees — so `entries.py` and `show_registration.py` both let the repeat through when `score_type == 'pattern'` and 409 otherwise. `entries_class_horse_uniq` still stops the *same* horse going in twice. Anything that offers a class picker has to respect this: the desk's `AddEntryForm` and the exhibitor's `AddClassEntry` both keep a pattern class on offer while that exhibitor still has a horse not already in it, and drop it otherwise. Money is per **entry**, not per class — a screen that sums `entry_fee_cents` over selected classes silently under-charges the moment a second horse goes in.
- **The exhibitor's class registration screen is the desk's entry form, pinned to the caller.** `frontend/app/shows/[id]/register/AddClassEntry.tsx` mirrors `admin/shows/[id]/desk/AddEntryForm.tsx` — one class picker, one horse picker, **Enter class**, committed on the press — and carries the same filtering, because a class you cannot enter is not worth offering. It posts to `POST /shows/{id}/register` rather than the staff endpoint: same form, same rules, different door, and the exhibitor comes from the session. What it replaced was every class in the show with a horse select on each row and one Submit at the bottom; do not reintroduce a batch picker, and do not make this screen the schedule again — `/shows/[id]/schedule` is the program, and it is linked from here. Two departures from the desk form are on purpose: classes grouped by show day, and inline confirmation on remove (a secretary is standing in front of the person asking; an exhibitor is on a phone).
- **Editing a waiver does not invalidate its signatures.** A show fixing a typo must not void what a hundred people already signed, and the app cannot tell a typo from a change of terms. Deleting and re-creating the waiver is the honest way to ask everyone again — and deleting it takes the signatures with it, because they were agreement to *that* text.
- Health status is judged **as of `shows.end_date`**, never today — `coggins_status(expiries, as_of)`, with `_paperwork_deadline()` picking the day. A Coggins that lapses between now and the show is the exact case staff need to chase; evaluating against today calls it valid until it is too late. Last day rather than first, because the horse is on the grounds all week. The `/profile` horse card is the one place that legitimately uses today — it has no show in hand.
- `ANTHROPIC_API_KEY` is optional. Unset (or an API outage, or an unreadable scan) degrades the upload form to manual entry, which is how it worked before extraction existed. Extraction must never be the reason someone can't file paperwork.
- **The exhibitor asks for a back number and gets it — the app does not queue the request.** `PUT /shows/{id}/register/back-number` writes `preferred_back_number` and, when nothing else at that show holds the number, `back_number` too. A number nobody else wants is not a decision anyone needs to make, and a "preference" the office still has to key in by hand is the workflow this replaces, with an extra table. The office keeps every power it had: the desk renumbers anyone, and `preferred_back_number` survives that so staff can see "asked for 42, has 87". Open only while the show is `PUBLISHED` — after that the numbers are printed and on backs. And `auto-assign` claims requested numbers before it fills the rest, because numbering straight through 1..N would undo every request in one click.
- A back number lives on `show_entries.back_number`, never on `entries.back_number` — the latter is a legacy column nothing writes, so it is NULL on every recent entry. Resolve reads through `backend/backnumbers.py` (`back_numbers_for_show` / `resolve_back_number`). Rendering `Entry.back_number` directly produces a silent column of dashes, which is exactly how it went unnoticed on four screens at once.
- A signed-out visitor opening `/shows/[id]` gets event details plus Register / Contact, not the class list. This gates the **browsing** path only — `/live`, `/schedule`, `/results` stay public because those are the at-the-rail screens people reach by QR code without an account. Don't "fix" the inconsistency by closing them. That page is also deliberately short on operational detail: the shavings policy lives on the sign-up screen, where the bags are actually ordered, not in the details a stranger reads to decide whether to enter.
- `?next=` redirect targets are sanitized by `safeNextPath()` (`frontend/lib/safe-next.ts`) before use: same-origin absolute paths only. The value comes from a URL a stranger composes, so `//evil.com` is an open redirect, not a path.
- **An aggregate screen quotes; it does not compute.** `show_desk.py` assembles the whole desk from `_load_financials` and `build_verification_checklist` rather than re-deriving a total or a check status, and its buttons post to the existing entry / back-number / side-pot / verification endpoints. A screen that sums `entry_fee_cents` itself is faster and will eventually disagree with the bill the exhibitor reads on My Shows; one that writes `entries` directly skips association validation and the closed-class rule. Applies to any future "one screen for X" — the aggregate is a read, not a second implementation.
- **A futurity class must carry `entry_fee_cents = 0`.** The futurity's fee tier supplies the per-class rate, because it depends on which category the entrant qualifies for and a class row cannot know that. A priced futurity class is billed twice — once in `class_lines`, once in `futurity_lines`. Nothing enforces it (the class screens know nothing about futurities), so the futurity screens warn on read instead: zeroing it server-side would hide a real mistake in the schedule, and the fix belongs on the class.
- **A futurity late fee is decided by `futurity_entries.entered_at`, never by today.** Same rule as `fee_rate_cents` and for the same reason: comparing the deadline against `now()` would drop a late fee on every enrollment already taken the moment the deadline passed, including people who entered in April. `is_past_deadline` on the exhibitor payload is the *quoting* question — what someone would pay entering right now — and is not what an existing enrollment is charged.
- **`per_show` is not `flat`.** A flat fee is charged once however many you have; a `per_show` fee is charged once **per thing reserved**, however long the show runs. An electrical hook-up sold as "$60 for the weekend" is `per_show` — two of them cost $120, and a three-day show still costs $60 each. Pricing it `per_night` silently doubles it on a two-day show, which is why the unit exists (migration 106).
- **Camping and the electrical hook-up are one line item, priced two ways.** `per_night` and `per_show` are how a venue charges for the same spot, not two products. The Lodging & Boarding setup step (Step 4) offers one camping line with that choice, and migration 108 folded the `hookup` fee code back into `camping`. It was two slots, which asked the manager which product they were selling and let one who answered both put two camping charges on the same bill with nothing to say so. On the exhibitor's picker both units sit under one "Camping & hook-ups" heading, with the noun (`nights` / `spots`) against the number being typed — that, rather than a separate heading, is what stops someone booking two *nights* of a $60-for-the-weekend hook-up.
- **A fee's price may change; its unit may not, once anybody has reserved it.** `PATCH /shows/{id}/fees/{fee_id}` returns 409 on a unit change when `show_entry_reservations` rows exist. `build_bill` multiplies rate × quantity and never reads the unit, so flipping camping from per night to per show turns "3 nights" into "3 spots" and reprices every booking with nothing in the data to record it — where a price change is decided honestly by `reserved_at`. `ShowFeeOut.reserved_count` (staff list endpoint only; the public price list does not report how many people entered) is what lets both fee editors lock the control rather than offer it and then refuse. Changing how a line is charged means removing the fee and adding it again, which drops the reservations in the open.
- Money is computed in one place: `build_bill()` / `office_charge_total_cents()` / `fee_rate_cents()` in `backend/billing.py`. The class-registration screen, the sign-up screen, the My Shows bill, and the Financials screen all read it, and `shows.office_charge_basis` is honoured there (`per_back_number` = one charge for the exhibitor, `per_horse` = × distinct horses). Do not re-derive a total in a router or a component. The show-wide rollup is `build_account()` (one exhibitor: bill + payments + balance) then `summarize_accounts()` over the results — **not** a SQL `SUM` over `entry_fee_cents`, which would be faster and would eventually disagree with the bill the exhibitor reads on My Shows.
- **Outstanding and credit are never netted against each other.** `summarize_accounts` sums positive balances into `outstanding_cents` and negative ones into `credit_cents` separately, because one exhibitor paying twice must not reduce what the show is owed by everyone else. `net_balance_cents` is the netted figure, kept alongside for the books. A single signed total would quietly under-report arrears.
- A refund is a **negative `show_payments` row**, never an edit to or deletion of the original payment. The original is a fact about money that moved; erasing it balances the account and loses that the money moved twice. `DELETE /shows/{id}/payments/{pid}` exists only for a row typed in error.
- Financials is the **show-office tier** — ADMIN, or the SHOW_SECRETARY / SHOW_MANAGER assigned to that show (`require_admin_or_show_admin` + `_assert_show_access`). `SCRIBE` and `GATE_STEWARD` are show staff too and are deliberately excluded: neither has any business reading revenue. "Show staff" is ambiguous in this app — check which tier before widening a money endpoint.
- Side pot money is reported **apart from** the exhibitor accounts on the Financials screen. Pot buy-ins are not part of `build_bill`, so folding them into a balance would make Financials and the exhibitor's own My Shows bill disagree. `billing.side_pot_money()` keeps them separate on purpose.
- A financial **report is data, not a page**: `backend/financial_reports.py` holds a slug → (title, description, builder) registry, and one generic frontend renderer draws whatever columns and rows it returns. Adding a report is a function in `_REPORTS` — no route, no component, no migration. Reports are built from the payload the overview already assembled and never query, so a report cannot quote a different number than the screen it was opened from.
- A fee's early-bird rate is chosen by `show_entry_reservations.reserved_at` — the day the exhibitor booked that line — **never by today's date**. Pricing off "now" would silently reprice a reservation the moment the deadline passed, which is the one promise an early rate makes. This is also why `PUT /shows/{id}/register/signup` updates surviving reservation lines in place instead of replacing them wholesale: recreating a row re-dates it, and someone who reserved in April would lose their rate by editing their arrival date in July. Read the rate through `fee_rate_cents(fee, reserved_at)`, never `fee.amount_cents` directly.
- An early rate is a **pair**: `early_amount_cents` without `early_deadline` (or vice versa) is a half-finished edit, not a price. `POST`/`PATCH /shows/{id}/fees` rejects it rather than storing a discount that would never fire, and also rejects one on a non-reservable unit — class entry fees live on `classes.entry_fee_cents` and are never reserved, so there would be nothing for it to apply to.
- Email is best-effort and optional. `backend/mailer.py` returns `None` when `SMTP_HOST` is unset and never raises. Every flow that mails a link must also return that link for copy/paste — an undelivered email must never be the reason a horse can't change hands or a request can't be answered.
- **A horse-access link finds the request; it does not authorize the answer.** `/horse-requests/[token]` requires the caller to be signed in as `approver_exhibitor_id`, and both `by-token` endpoints 401 without a session and 403 for anyone else. This follows directly from the rule above: because the link is handed to the **requester** so an undelivered email can't strand a horse, treating possession of it as consent let somebody approve their own request to take a horse they don't own — the one thing the table exists to prevent. The link still travels by any route that works; it just picks the request out of the table rather than granting anything. A `link` request against an owner with **no account** is refused at creation for the same reason: nobody could ever answer it.
- **An exhibitor's show page is a menu; a scribe's is a class list.** `/shows/[id]` renders `ExhibitorShowHub` for everyone who cannot score, and the old class list only for `ADMIN` / `SCRIBE`. For a scribe the class numbers *are* the menu — each row links into a scribe screen — but for everybody else forty rows of something to read buried the four things they came to do. The class list is one tile away at `/shows/[id]/schedule`, which was built for it.
- **The show bill is generated, not uploaded.** `/shows/[id]/showbill` is drawn from the show's own classes, judges, fees and policies, and "download" is the browser's print-to-PDF (plus a CSV of the class list for spreadsheet work). An uploaded PDF would be a second source of truth that goes stale the moment a secretary adds a class — and worse than no PDF, because people trust the one they printed. The same reasoning is why `GET /shows/{id}/fees/public` exists: the price list on the bill has to be the price list the app charges from.
- A paperwork verification is never taken from the client. `POST /shows/{id}/verifications` accepts the *subject* only; the backend reads the current value off the record and stores that. A caller able to name the value it "verified" could attest to a number nobody has on file. For the same reason `verified_value` is a snapshot, not a live join — that is the whole staleness mechanism.
- **Staff filling in an exhibitor's profile writes the profile, not a per-show copy.** `PATCH /shows/{id}/exhibitors/{exhibitor_id}/emergency-contact` puts the contact on `exhibitors`, because who to telephone about a person is not a fact about one weekend and a per-show duplicate would go stale the moment they change their number. `PATCH /exhibitors/{id}` is ADMIN-or-self, which is why this exists at all — a secretary could not otherwise take a number over the counter without asking somebody to go and edit their own account. Both halves or neither: a name with no number still reads as missing everywhere it is checked, so accepting one would let staff save something and watch the row go on saying "no emergency contact".
- Show staff creating a horse for an exhibitor is scoped to that show's roster, not to staff rank. `POST /shows/{id}/exhibitors/{exhibitor_id}/horses` 403s unless the exhibitor has a `show_entries` row or a class entry at that show. The horse is owned by the exhibitor and linked via `exhibitor_horses` — ownership alone does not put it on their profile list, which reads `created_by_exhibitor_id` **or** a link row.
- Linking a horse someone else owns is not a one-click action. `POST /exhibitors/{id}/linked-horses` only links outright when `horses.owner_exhibitor_id IS NULL`; otherwise it returns `409 OWNER_APPROVAL_REQUIRED` and the caller goes through `horse_access_requests`.
- Who rides a horse and who trains it are the **owner's** calls, and creating the record is not a way around that. `_check_horse_access` (ADMIN or `owner_exhibitor_id`) covers `PATCH /horses/{id}` and the rider endpoints; `POST /exhibitors/{id}/created-horses` drops the trainer fields unless the caller claims the horse, and opens a pending `link` request instead of self-attaching when the owner named already has an account. An open trainer field is not a small thing — naming a trainer who isn't on file *creates* a `trainers` row. See "Who May Change A Horse" in `docs/auth.md`.
- Judge details are not per-show data. `show_judges` carries no name or contact columns since migration 085 — read them through `judge`, and resist re-adding a per-show copy "just for this screen".
- The score-entry role is **`SCRIBE`**, not "Ring Steward" — do not rename it again. In the horse show world a *scribe* is the person at the judge's shoulder writing down every score and penalty the judge calls; that is what this role does. A *ring steward* (ringmaster) works the arena floor — safety, halter lineup, calling gaits, carrying the signed card to the office — which is much closer to what `GATE_STEWARD` already does. Calling this one `RING_STEWARD` would produce two unrelated "stewards" and hang an arena-floor title on a scoring screen.
- `classes.class_number` is **published identity**, not a display index. It appears in the show program, on entry forms, and is how the gate and exhibitors refer to a class, so it is never renumbered to match a filtered or reordered view. The show page folds finished classes away for scribes on an active show — a list starting at "14" is that fold, not a numbering bug. Fix the affordance, never the numbers.
- **Autosave is only safe because of the publish gate.** The scribe forms have no Save button; they commit the whole class on a 1.5s settle. That is only tolerable because results land in a draft first — a placement card reads 1, _, 3 until the last horse is entered, and results go straight to public at-the-rail screens. Do not add an autosaving surface that writes results without checking `results_published_at`, and do not "simplify" the gate away. The same reasoning moved the gap warning from Save to Post: mid-entry gaps are now normal.
- **Audit rows start at publish, not at first keystroke.** `bulk_save_results` writes `result_audit` only when `results_published_at` is already set. Before that there is no published value for an edit to have changed, and autosave would otherwise write a row per settle — turning the record of who changed an official placing into keystroke noise. Corrections *after* posting are the thing the audit exists for, and those are still captured.
- The results bulk save is **delete-all-then-insert-all within one judge's card**, so two in flight can interleave and lose a score. `useAutosave` keeps one request at a time and queues the next; anything else calling that endpoint on a timer needs the same care. The `judge_id` on the request envelope is what scopes the delete — omit it and the save lands on the unattributed card rather than the judge's, which looks like the placings vanishing.
- Reading results as staff requires **passing auth headers** — `fetchResults(showId, classId, headers?)`. The endpoint returns `[]` for an unposted class to an anonymous caller, which is the gate working; a staff screen that forgets the headers silently renders an empty card over a real draft.
- What the scribe screen captures today is the **final number**, not the judge's card. `results.raw_score` holds one score per entry per judge, which is the office tabulation step. Real scribing is maneuver-by-maneuver (base 70, maneuver scores, penalty tiers of 3/5/10, Form & Effectiveness, judge comments) and is not modeled yet. Open work, not an oversight to paper over.
- The app **does not combine judges' cards into an official result**, and adding one is a rules decision, not a display improvement. Each judge places independently and they disagree; the public class page orders rows by mean placing purely so the sheet reads top-down and says so on the page. Side pot standings currently take the entry's *best* card per class — deterministic and identical to the old behaviour on the single-judge shows pots have actually run on — but show bills settle multi-judge pots "from combined judge score sheets", which is a sum. Changing it would silently reprice existing pots, so it needs a deliberate call.
- Unassigning a show judge who has already filed placings returns **409**, not a cascade. `results.judge_id` is `ON DELETE RESTRICT` on purpose: the answer to "this judge has 40 placings on file" is never to delete them as a side effect of tidying the panel.
- **A security-answer lockout closes the reset route, never the login.** Signing in with the password clears the counter, and an admin password reset clears it too. Locking the account itself would let anyone lock anyone out by guessing at their question five times — an outage handed to strangers, on the screen that exists to end outages. While locked the **question is withheld as well**, since the prompt is the half that hints at the answer.
- **The security question is never shown to an admin** — `GET /users/{id}/security-question` reports only whether one is set, when, and whether it is locked. An admin can already reset the password outright, so displaying a self-written question (which usually hints at its own answer) adds exposure and no capability. Admins may `DELETE` a forgotten one; they cannot set a replacement, because that would mean knowing the answer to somebody else's account.
- Do not create an `EXHIBITOR` user without also creating the linked `exhibitors` row.
- Do not create a `TRAINER` user without also creating or linking the matching `trainers` row.
- `cert_org_users.Org` uses a capital `O`.
- `OPEN` is an unaffiliated **show type** only. Since migration 080 it has no `associations` row at all, so it can no longer leak into certification or registration-number pickers — the old `UNCERTIFIED_CODES = ['OPEN']` guards were removed as dead code. Do not re-add OPEN to `associations`.
- Do not reach for `show_types` when you mean an affiliation. Registration/membership numbers belong to `associations` (breed or club); `show_types` is show configuration. Clubs (NSBA, WSCA) are deliberately **not** show types — an NSBA-approved show is an OPEN or breed show carrying NSBA sanctioning via `show_sanctioning`.
- Horse age is derived, not stored.
- Deleting a horse preserves entry history by setting `entries.horse_id` to `NULL`.
- The repo has historical duplicate migration numbering around `024_*`; preserve filenames and ordering behavior.
- `ConfirmDialog` exists but is no longer the preferred delete pattern.
- `classes.score_type` is derived from `division.default_score_type` at create time when not explicitly set. APHA/AQHA bulk imports and the free-text class-list importer are **auto-routed** via [backend/rules/disciplines.py](backend/rules/disciplines.py): the class name is classified by ordered keyword match into a discipline (Division) with a default `score_type`. For APHA/AQHA catalog imports the std-class `division` column is used as the section (bracket); for pasted class lists the secretary can provide a default bracket or per-line bracket using `Class Name | Bracket`. Divisions/sections are created on the fly and the (div, sec) membership is registered. Anything the classifier can't match (currently 0% of AQHA/APHA std classes) falls back to "Unassigned". Side pots with `sum_scores` only see `pattern`/`time` classes.
- Migration 061 made `classes.division_id` and `classes.section_id` NOT NULL and enforces `(division_id, section_id)` membership in `division_sections` via a composite FK. Code that creates a class must either provide a valid pair or call `_get_or_create_unassigned()` from `routers/classes.py`. Removing a section from a division it still has classes in returns 409.
- Migration 048 dropped `class_templates` and the `category` concept; "Division = discipline" and "Section = bracket" are the canonical vocabulary. Per-show `divisions` rows that pre-date 048 may still contain bracket-named entries — secretaries clean those up in the Setup UI.
- For `pattern`/`time` classes the scribe enters `raw_score` and the backend recomputes `place` and `is_tie` on insert/update/delete — **grouped by judge**. Every judge marks the same run on their own sheet, so a 71.5 from one and a 71.5 from another are two firsts, not a tie; pooling them would also make each judge's placings shift as other judges filed. Audit rows are only written for `placement` classes.
- Settling a side pot is irreversible — `status` flips to `settled`, payouts are written, and edits/deletes are blocked.
